# CLAUDE.md

Guidance for agents working in this repository. The REST API, upload behavior and environment variables are documented in [README.md](README.md), local setup in [DEV.md](DEV.md), and the Helm chart in [its README](deploy/charts/cbom-repository/README.md).

## Repo map

| Path | Purpose |
|------|---------|
| `cmd/cbom-repository` | Entry point: reads the config, connects to S3 and wires the service, health checks and HTTP server. |
| `internal/env` | Environment-variable contract (`APP_*`, read with `envconfig`) and its validation. |
| `internal/http` | `gorilla/mux` routes under `APP_HTTP_PREFIX`, handlers, media-type parsing, `application/problem+json` errors and optional CORS. |
| `internal/service` | Upload, validation against the CycloneDX JSON schemas embedded from `schemas/`, crypto statistics and search cursors. |
| `internal/store` | S3 access through `aws-sdk-go-v2` and its transfer manager; `mock/` is generated by mockgen. |
| `internal/health` | Liveness and readiness; readiness runs the storage check (`HeadBucket` on the bucket). |
| `internal/log` | `slog` handler that adds attributes stored in the request context to each record. |
| `api/openapi.yaml` | Hand-maintained API description, not used by the code; update it with every API change. |
| `deploy/charts/cbom-repository` | Helm chart; `ci/develop-values.yaml` holds the values for `ct install`. |
| `tests/helm` | Python `unittest` checks of the chart rendered with `helm template`. |

## Commands

Run these from the repo root before considering a change done:

- Build and vet: `go build ./...` and `go vet ./...`
- Tests: `go test -race ./...`. All tests are unit tests with S3 mocked or faked, so no services are needed.
- Lint: `make lint` (golangci-lint `@latest` with `.golangci.yml`). It also writes `golangci-lint-report.xml`, the report Sonar reads.
- Mocks: `make mockgen` regenerates `internal/store/mock` and must leave no diff.
- Vulnerabilities: `go run golang.org/x/vuln/cmd/govulncheck@latest ./...`
- Image: `docker build -t cbom-repository .`, then scan it as described in [Release image gate](#release-image-gate).
- Chart tests: `helm dependency build deploy/charts/cbom-repository`, then in a virtualenv `pip install --require-hashes --only-binary=:all: -r tests/helm/requirements.txt` and `python -m unittest discover -s tests/helm -p 'test_*.py'`.

## Release image gate

The org Trivy policy blocks vulnerabilities only in tag builds. On pull requests and `main` they only warn and are listed in the job summary, so a vulnerable Go toolchain or module passes CI and first fails when a release is tagged. Other findings, such as a leaked secret, fail every build.

- The policy is `.github/actions/resolve-trivy-config/trivy.yaml` in the public `OmniTrustILM/.github` repository: CRITICAL and HIGH vulnerabilities that have a fix, plus secrets. The workflows use it as is, without a repo-local override.
- Before tagging, download it from `https://raw.githubusercontent.com/OmniTrustILM/.github/main/.github/actions/resolve-trivy-config/trivy.yaml` to a file outside the repo and scan the image with it: `trivy image --config <file> cbom-repository`.
- The Go standard library in the image comes from the Dockerfile builder image, not from the `go` directive in `go.mod`, so a Go security release needs a builder image bump.

## Conventions

- When adding or updating a third-party GitHub Action, pin it to a full commit SHA with the version as a comment (`owner/action@<sha> # vX.Y.Z`); Sonar rule `githubactions:S7637` flags tag references. The org's reusable workflows are called on `@main` in `publish_docker.yaml` and `test_docker_image.yaml`, and `sonar-project.properties` exempts them from the rule.
- Renovate runs with the org-wide config (`renovate.json` in `OmniTrustILM/.github`) and limits how many pull requests it keeps open, so some updates have no PR yet. A dependency refresh checks every pin, not only the open Renovate PRs.
- Python bumps in the chart workflows wait until PyYAML, pinned by wheel hash in `tests/helm/requirements.txt`, ships wheels for the new Python version.
- A pull request that changes the chart needs a `-develop` chart version (between releases it is `<release>-<n>-develop`, e.g. `1.1.0-1-develop`); Test Chart enforces this for branches whose name does not start with `release`. The release PR sets `version`, `appVersion`, `image.tag` in `values.yaml` and the `image.tag` row of the chart README to the release version.
- A new `APP_*` variable goes into the README table, and into the chart's deployment template and values when Helm should set it.
- Commits: one plain description of the change, signed off with `git commit -s` (the DCO check runs on every PR), with no co-author trailers and no mention of AI tooling.
- Pull requests need a Copilot review: the Require Copilot Review check fails until `copilot-pull-request-reviewer` has reviewed or commented.

## CI checks

- **Check PR** (`check_pr.yml`): golangci-lint, `go mod verify`, build, vet and `go test -race` with coverage.
- **SonarCloud** (project `ilm_cbom-repository`): after Check PR succeeds, `dispatch-sonar.yml` starts `sonar.yml` from the default branch, and `sonar.yml` reads `sonar-project.properties` from the base branch, so changes to either take effect only after merge. Issues and measures are readable without a token through the public API, e.g. `https://sonarcloud.io/api/issues/search?componentKeys=ilm_cbom-repository`.
- **Sonar Main** (`sonar_push.yml`): analyzes `main` on every push, which keeps the SonarCloud main branch, the baseline for pull request analysis, current.
- **CodeQL** (`codeql.yml`): Go and GitHub Actions analysis.
- **Test Docker image** (`test_docker_image.yaml`): builds the image and runs the Trivy scan, where vulnerabilities only warn.
- **Test Chart** (`test_chart.yaml`): runs for changes to the chart, `tests/helm` or the workflow itself, with the Python chart tests, `ct lint` and `ct install` on kind.
- **Require Copilot Review** and **DCO**.

For a local Sonar check, run a throwaway `sonarqube:community` container, create a token on it, generate `coverage.out` (`go test -race -coverprofile=coverage.out ./...`) and the lint report, and run `sonar-scanner -Dsonar.host.url=http://localhost:9000 -Dsonar.projectKey=cbom-repository-local` with `SONAR_TOKEN` set to that token. Its rules differ from SonarCloud's, so SonarCloud on the PR stays authoritative.

## Local-only files

Build and analysis outputs (`coverage.out`, `golangci-lint-report.xml`, `.scannerwork/`, packaged charts) and local working documents (`docs/superpowers/`, `.superpowers/`) are gitignored; check `git status` before staging. Code, comments and commits never refer to the working documents.
